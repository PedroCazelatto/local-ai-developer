# Core mental model: one model, many context windows

There is exactly **one** local Ollama model. Everything else is context windows.

- Ollama's chat API is **stateless**. The model knows only what is in the `messages` array sent on a
  given call — there is no hidden server-side memory. "Memory" is the orchestrator replaying the
  accumulated history every call (`OllamaClient.chat`/`stream` in
  [src/core/llm/client.ts](../src/core/llm/client.ts)). `num_ctx` (`OLLAMA_NUM_CTX`) is a hard token
  ceiling; exceed it and Ollama silently drops the oldest tokens.
- A **"subagent" is not a new model** — it is a fresh, empty `messages` array with a one-shot system
  prompt plus a single task, run against the same Ollama, then discarded. Isolation is just a
  separate list. It inherits **its master phase's** tool array minus the three sub-agent tools (so it
  cannot nest), never the full registry — a sub-agent must not be a way around its master's gate.
- A **phase** is the unit of work and the unit of instruction. Each phase has an instruction set (its
  markdown under [rules/](../rules/)) that configures the window it runs in. Elsewhere these are
  called "skills" or "personas" — in this project the single word is **phase**.

So the design is not "personas vs. skills." It is: **which phases the user drives interactively, and
which the orchestrator spawns automatically** — see [phases.md](phases.md).

## Memory model

Each phase has its **own isolated message history**. Switching phases saves the active history and
loads the target's — no cross-phase leakage, no auto-clear. The user owns the decision to wipe
history. Spawned execution windows (Worker/Reviewer/Retro) start from an **empty** history and are
discarded after their task — except the Worker, whose history persists *across the fix loop* (so it
remembers prior attempts and Reviewer feedback) and is discarded when the task closes. Those windows
are RAM-only: they persist nothing, so everything below describes the interactive phases.

### A phase context is a record, not a file

A phase's history lives in a **context**: an addressable, titled row, not a scratch buffer. A context
can be listed, described and reopened by address, which is what lets a phase — or the user — decide to
*continue* an earlier line of work instead of starting over.

- **Address:** `<phase>/<8-char UUID>`, e.g. `design/7a888b1f`. Ids are UUIDs generated by the
  database; the address is a unique leading prefix, and any prefix that identifies exactly one context
  is accepted.
- **Title:** one line of at most 60 characters describing **why that context exists** — not what its
  first message said. It is written once, after the context's first prose answer, by a **throwaway
  one-shot** (the same device `composeCommitMessage` and `search_rules` use), so it costs the working
  phase no context. Its rules live in [rules/prompts/context-title.md](../rules/prompts/context-title.md).
  A context that never produced a prose answer stays untitled; nothing invents a description for it.
- **Storage:** one SQLite database per project, `projects/<name>/.orchestrator/memory.db`, with a
  `contexts` table and a `messages` table. It lives inside the project repo, so memory travels with the
  project. Turns are buffered in RAM and written once per assistant turn, in one transaction.

### What survives, and what does not

- **A restart starts a fresh context.** Every `run start` opens a new context for a phase; the previous
  one keeps every turn and stays reopenable by address. A session does *not* silently resume where it
  stopped — continuing an earlier line of work is a deliberate act, not a default.
- **Which context is live is session state, not data.** Nothing in the database marks a context
  "current"; the live context per phase is held in RAM and dies with the process.
- **A context is created lazily,** on the first flush — that is, the first time the model answers. A
  phase the user never talked to leaves no row, and a session with no model selected creates nothing.
- **`/clear` opens a new context** rather than wiping anything. The context it sets aside is named in
  the confirmation, and `/resume` reopens it. Other phases are untouched.
- **Nothing is ever deleted.** Not by `/clear`, not by the summarization failsafe, not by a `num_ctx`
  change. Every mechanism below hides turns from the *live view*; the rows stay.
- **Token-threshold failsafe:** when a phase's history crosses `SUMMARIZATION_THRESHOLD_RATIO` of
  `OLLAMA_NUM_CTX`, the orchestrator summarizes the oldest turns and replaces them with a single
  summary entry. The originals stay in the database, pointed at the summary that stands in for them.
  This is a safety valve against VRAM exhaustion, not normal operation.
- **A `num_ctx` change hides every earlier context.** Each context records the exact `OLLAMA_NUM_CTX`
  it was written under, and a context written under a different ceiling is neither listed nor
  reopenable — Ollama silently drops the oldest tokens past the ceiling, so replaying a 32k history
  into an 8k window would leave the phase reasoning from turns it can no longer see. Restoring the old
  value brings them back; `OLLAMA_NUM_CTX` is read once at boot, so the change can only ever be
  detected there.
- **Which model wrote which turn is recorded per turn,** so a mid-session `/models use` is visible in
  the history rather than inferred. No model is blocked from reading another's turns.
- **Documentation files** (rules, plans, specs) exist for one-time reference or human reading — they
  are not loaded into every prompt.

The trade-off in buffering turns and flushing per assistant turn, stated plainly: a kill mid-turn loses
the turn still in flight. Committed turns are fsynced (`synchronous = FULL`).

Minimize persistent context to save tokens; local inference is VRAM-bound. Cross-phase communication
goes through the inbox ([phases.md](phases.md)), not memory.

The summarization trigger keys off **exact** token counts from Ollama, never estimates — a
VRAM-safety invariant; see [constitution.md](../constitution.md).
